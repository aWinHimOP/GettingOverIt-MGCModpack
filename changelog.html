1.28.0-beta.40 正式频道 · 2026-11-16

加「帧时间 / GC / 我方耗时」探针，用真机数据定位「一顿一顿」。

新增

  • 探针只在 MGCModpack/update/perfprobe.txt 存在时启用（正式包没有该文件 ⇒ 零开销）；
  • 每秒一行日志：帧数 / 平均与最大帧时间 / 超过 50·100·250ms 的帧数 / 各代 GC 次数 / 堆占用 / 我方代码耗时；
  • 长帧单独记明细（>100ms），带场景名，便于对上当时的操作；
  • skipmods 开关：写进 perfprobe.txt 后跳过所有 mod 每帧派发，用于 A/B 对照。

实测结论（小米 Note 3 / SD660 / Adreno 512 / 1080p）

  • 稳定期 avg ≈ 21ms（≈48fps），max 26~30ms；把分辨率降到 960×540 后 仍 20.4ms ⇒ 不是 GPU/填充率瓶颈；
  • 跳过全部 mod 派发后 仍 20.6ms ⇒ 不是 mod 的每帧代码；我方代码实测 0.00ms/秒；
  • 每 ~46 秒一次 gen1 GC（堆 27.8MB→10.4MB，尖峰 40~64ms），分配速率 ≈0.4MB/s（这部分不是 MGC 产生）。

判读：主线程卡在 16.7ms 预算之外 ⇒ 隔几帧错一次 vsync（judder），再加 46 秒一次的 GC 尖峰 —— 这就是「一顿一顿」的两半。详见 07_文档/卡顿测量-探针结论.md。

1.28.0-beta.38 正式频道 · 2026-11-16

性能第一批：把「每帧找对象 / 每帧反射 / 每帧 IO / 每帧写布局」四件事按住。

改了什么

  1. 对象查找改缓存：游戏原面板（MainMenu(Clone) 下的 userInfoPanel）存进静态字段，只有对象被销毁（换场景/重开一局）才重取；Player 也改成缓存（原来 Update/FixedUpdate/LateUpdate/OnGUI 每帧各查一次全场）；
  2. 反射改「方法指针」：Type.GetType/GetField/GetMethod 结果只解析一次；读 RKS 用 Delegate.CreateDelegate 绑定成 Func<float>，之后就是普通委托调用（不再走 MethodInfo.Invoke）；只有管理器实例换了才重绑；
  3. 每帧 IO 干掉：头像目录扫描结果按「目录 mtime」缓存，换头像时失效；头像缓存刷新从 60Hz 降到 2Hz；
  4. 信息栏刷新降频：昵称/RKS 从「每帧抄一次」改成 10Hz，刚显示那一帧强制刷；
  5. 布局只在变化时写：AutoLayoutHeight 原来每帧写 sizeDelta（触发 UGUI 整块重排），现在高度没变就不写；
  6. IMGUI 少调：ModManager 只对真正重写了 OnGUI 的 mod 派发（基类空实现直接跳过，按类型只反射一次）；
  7. 通关页不重复算：分段表用「快照指纹」短路，数据没变就不归一化、不重绘（每帧省下十几组数组与几十个字符串）。

为什么

真机每帧固定在做：约 8 次全场 GameObject.Find、6~10 次反射、1 次目录扫描、1 次布局重建。这些都不是业务必需，全部改成「一次缓存 + 失效重取 + 事件/节流触发」。

1.28.0-beta.36 正式频道 · 2026-11-16

头像常驻内存；场景重置 / 重开一局后自动重贴自定义头像，不再变回默认。

根因

换头像时只调了 UserInfoManager.SetAvatar()，没在内存里留一份，也没通知面板视图缓存；恢复逻辑又只在启动跑一次（还带一次性开关）。场景重置后游戏把头像表现恢复成占位环，就再没人把自定义头像贴回去 —— 于是"重开一局头像没了"，而且每次都要重新读盘解码。

改法

  1. AvatarManager._activeAvatar 常驻内存，换头像/启动恢复时写入；
  2. 新增 SyncActiveAvatarToCurrent()：每帧比对「UserInfoManager 实例 id + 场景名」，变了就重贴一次；
  3. 同场景内被重置（重开一局可能不换场景名、复用实例）时，发现原面板头像是占位环就补一次，限速 1 秒/次，不会变成每帧 SetAvatar；
  4. 换头像/恢复时同步刷新面板视图缓存（SetCachedHeadSprite），副本立刻是新头像；
  5. 重置为预设头像时清空内存缓存，避免旧自定义头像被贴回来。

验证方式

设自定义头像 → 重开一局 / 重进场景：右上角仍是自定义头像（圆形），日志有 [PlayerSetting] 已重新贴自定义头像（场景=…）。

1.28.0-beta.35 正式频道 · 2026-11-16

显存爆炸的真凶找到了：自定义头像被每帧重新解码。另外修好通关页分段表的差值。

证据（用户实测）

  • 设置自定义头像 → 进菜单后 GL mtrack 每秒涨几十 MB，最后被 lowmemorykiller 用 signal 9 杀掉；
  • 删掉自定义头像 → 完全稳 60 帧，不再闪退；
  • 通关页右上角头像不是圆的、还是默认头像（退出去又能看到自定义头像）。

根因

UserInfoPanelView.CacheLiveAvatar() 挂在 UserInfoPanelFollower.LateUpdate 里 每帧跑。发现游戏面板上还是占位圆环（FilledRingCursor）时，会走"从磁盘读一张"的兜底 —— 于是 每帧 new Texture2D + Sprite 解码一张头像，且每帧都不销毁旧的 ⇒ 每秒泄漏 60 张头像贴图 ⇒ 显存爆炸。没设自定义头像时这段不执行，所以"删掉就正常"。

改法

  1. 新增 LoadLocalAvatarSpriteCached()：按「路径 + 修改时间」只解码一次，替换时销毁旧贴图；
  2. 解码后 裁成圆形（256×256，中心取样 + 圆形 alpha 遮罩）——通关页副本没有圆形遮罩，方形贴上去就是"头像不圆"；
  3. 占位圆环不再覆盖已缓存的自定义头像；
  4. 新增 RetryRestore()：启动时 UserInfoManager 没就绪也不会丢头像，之后每帧补恢复一次，成功即停；
  5. 通关页分段表：ShowSnapshot() 以前无条件把本局分割换成 PB 那套 ⇒ 本局值 == 对比基线 ⇒ 差值恒 +0.000、Segment 列显示 PB 段。现在只有本局没数据才用 PB 兜底。

验证方式

① 自定义头像挂 1 分钟：GL mtrack 不涨、稳 60 帧；② 通关页头像圆形且是自定义那张；③ 重启后头像还在；④ 通关页差值真实（如 Tutorial +2.4s）。

修「mod 开关点了不变色，前后都是灰的」：不是没给颜色，是颜色写给了不存在的组件。

根因

  4. 新增日志 [ModUIManager] 开关底色节点: 模块名 → 节点名（RoundedRect/Image/…），下次一看就知道点到了谁。

验证方式

1.28.0-beta.32 正式频道 · 2026-11-16

通关页：左上角第一行加版本号；并修真因 —— 通关提交分段纪录赶在"最后一段补算"之前，导致存档是"没完赛"的。

根因

WinDone 有多个订阅者（分段存档 / RKS / 统计 / UI），谁先跑没有保证。游戏是先发 win.done、后跑 UpdateTimer，最后一段要靠 FinalizeRunAtWin(总用时) 补算；如果存档模块排在前面，提交出去的就是「最后一段还是 0、finished=false」的快照 ⇒ 通关页显示不全、差值列空白。

改法

  1. 提交前自己先结算一次（FinalizeRunAtWin 幂等：已结算会直接返回 false），不再依赖订阅顺序；
  2. 结算拿不到总用时/计时器已不在时，打明确日志，方便下次定位；
  3. 通关页左上角第一行加 版本：1.28.0-beta.xx。

验证方式

修法

大文件（≥4MB，地图包 38MB 属于这类）不再用 UnityWebRequest，改成 后台线程 + HttpWebRequest：

  • 网络 IO 全在后台线程，主线程只轮询进度 → 不可能卡住 UI；
  • 64KB 流式写盘，40MB 也不占内存；
  • Range 续传走标准 HTTP 头，不经过 Unity 的 native 网络层；
  • 连接用完即关（KeepAlive=false），避开这台设备「复用连接导致第二个请求瞬间失败」的毛病。

小文件（模组包 127KB 等）仍走原来的分块逻辑，行为不变。

已知风险

这条路径依赖 Mono 的 TLS 实现，如果某些机型上证书握手失败，会在日志里写明原因（后台线程下载失败: …），不会卡游戏。

现场长什么样

崩溃日志停在半行（块详情 … error=Request tim），之后 29 秒**一行日志都没有**——主线程停了。这期间正在反复重试下载 38 MB 地图包，每次都 code=206 实收=0 Request timeout。

根因

每处理一个响应，代码要访问 3 次 UnityWebRequest.downloadHandler.data（打日志 1 次、写盘 1 次、ConsumeResponse 里 1 次）。当请求已经超时、底层还在收/还在等时，这个属性会阻塞调用线程——而调用它的正是主线程，于是画面定格、日志断在半行，30 秒后被系统杀掉。

修法

  • 响应体只取一次：拿到 body 后全程复用，不再反复访问 downloadHandler.data。
  • Dispose 前先 Abort：请求没真正结束时直接 Dispose，在 Android 上会卡/崩（原生线程还在读），先掐断底层传输再释放。

beta.6 修掉了「进度归零」，真机日志又暴露出两个新问题：一处把好数据当成坏数据扔掉，一处会吃满内存。

「续传数据超出总大小」——本来是对的包，被当成坏包删了

现象：下载器日志反复出现 续传数据超出总大小（130827 > 127952），已删除 .part，进度条回到 0，重试四次后报失败。

修法：超出时不再删，改为以实际大小为准继续走收尾；真正的判据交给 sha256 校验（对不上才删）。体积只是提示，校验和才是门。
